# F4.2 / VB-8H — Campaign Pause/Resume & Execution Lifecycle Ownership

## 1. Executive Summary

The F4.1 framing was **partly wrong**, and re-deriving it from the code changed the work
substantially.

- **B9 was misdiagnosed.** It reported `RUNNING → COMPLETED` and `RUNNING → FAILED` as
  producer-less. On the **execution** side that is false — VB-8D created those
  producers in `CampaignExecutionOrchestrator`. The real B9 defect is on the
  **campaign** side, and it is worse than "no producer": the transition table withheld
  three edges behind a `SYSTEM_DRIVEN_TRANSITIONS` set on the stated assumption that
  *"the execution engine"* would drive them. No such producer exists or should exist,
  and the resulting model was incoherent — `RUNNING` was reachable only from `PAUSED`
  (because `PAUSED → RUNNING` was never withheld), and once entered could never reach a
  terminal state.
- **A new HIGH defect was found that F4.1 did not list.** The dispatch gate was
  `campaign.status == PAUSED`. That silently assumed PAUSED is the only way to stop
  dispatch — but `SCHEDULED → ARCHIVED` is operator-legal on a campaign that can own a
  `RUNNING` execution, and `ARCHIVED` is terminal. **Archiving a campaign left it
  dialling indefinitely.** Nothing else in the engine consulted the campaign there.
- **B10 is real** and is solved by derivation, not persistence.

Three changes, all narrow. **No migration, no new module, no new infrastructure, no
snapshot-model change, and no telephony change.**

## 4. Campaign Lifecycle Audit

`CampaignStatus` has **seven** states, not the five in the brief:
`DRAFT, SCHEDULED, RUNNING, PAUSED, COMPLETED, FAILED, ARCHIVED`.

`CampaignService.LEGAL_TRANSITIONS` is the table. Every transition in it, with its real
producer:

| From → To | Producer | Actor | Reachable before VB-8H? |
|---|---|---|---|
| DRAFT → SCHEDULED | `changeStatus` | operator | yes (validates activation) |
| SCHEDULED → DRAFT | `changeStatus` | operator | yes (the documented edit unlock) |
| SCHEDULED → PAUSED | `changeStatus` | operator | yes |
| SCHEDULED → RUNNING | — | **none** | **no** (withheld) |
| SCHEDULED → ARCHIVED | `changeStatus` | operator | yes |
| RUNNING → PAUSED | `changeStatus` | operator | only from PAUSED |
| RUNNING → COMPLETED | — | **none** | **no** (withheld) |
| RUNNING → FAILED | — | **none** | **no** (withheld) |
| PAUSED → SCHEDULED | `changeStatus` | operator | yes (resume) |
| PAUSED → RUNNING | `changeStatus` | operator | **yes — the only way in** |
| PAUSED → ARCHIVED | `changeStatus` | operator | yes |
| COMPLETED → ARCHIVED | `changeStatus` | operator | unreachable before (COMPLETED unreachable) |
| FAILED → ARCHIVED | `changeStatus` | operator | unreachable before |

**The incoherence:** `RUNNING` was enterable only from `PAUSED`, and its only legal exits
were `PAUSED` (allowed) and the two withheld terminal edges. So an operator could put a
campaign into `RUNNING` and it could never finish.

## 5. Execution Lifecycle Audit

`CampaignExecutionStatus`: `REQUESTED, RUNNING, COMPLETED, FAILED, CANCELLED`.
Endpoints: `POST /{id}/executions`, `GET /{campaignId}/executions/{executionId}`,
`GET /{campaignId}/executions`. **There is no execution status-change endpoint** — no
operator path to any execution state.

Producers, all in `CampaignExecutionOrchestrator`:

| Transition | Producer | Line |
|---|---|---|
| → REQUESTED | `CampaignExecutionService.execute` (creation) | — |
| REQUESTED → RUNNING | `startExecution` / `startExecutionAsSystem` | 269 |
| RUNNING → COMPLETED | `reconcileExecutionInternal` (all attempts terminal, ≥1 completed) | 539 |
| RUNNING → FAILED | `reconcileExecutionInternal` (all terminal, none completed) | 541 |
| REQUESTED → FAILED | `startExecution` when readiness fails for a non-deferable reason | 261 |
| → CANCELLED | **none** | — |

`COMPLETED`/`FAILED`/`RUNNING` are all owned by exactly one component. Good.

## 6. B9 Analysis

**B9 decomposes into three distinct facts, and the audit only got one of them right.**

- **B9a — CAMPAIGN (real, and the significant one).** `SYSTEM_DRIVEN_TRANSITIONS` =
  `{(SCHEDULED,RUNNING), (RUNNING,COMPLETED), (RUNNING,FAILED)}`, each rejected with
  *"Transition X -> Y is performed by the execution engine."* No such engine path
  exists. **Decide: no producer.** Campaign is operational control state;
  `CampaignExecution` is the run record. With multiple executions allowed per campaign,
  no single campaign status could faithfully mirror them all, so an engine-driven
  campaign status would be ambiguous by construction.
- **B9b — EXECUTION `RUNNING`/`COMPLETED`/`FAILED` (audit was wrong).** Producers exist
  and have since VB-8D. No change needed.
- **B9c — EXECUTION `CANCELLED` (real, deferred).** Zero references in `src/main`. No
  producer. Deferred: *who* cancels and *under what conditions* is a product decision
  with no stated requirement, and inventing an operator cancel endpoint would be exactly
  the "artificial state mutation" the brief warns against.

## 7. B10 Analysis

Why can an execution remain `REQUESTED`? Traced:

1. `CampaignExecutionService.execute` **re-checks readiness and rejects creation** if the
   campaign is not ready. So an execution can only be *created* while its campaign is
   ready — i.e. executable.
2. Therefore the **only** way one stays `REQUESTED` is that the campaign subsequently
   left the executable set. `startExecution` calls `isDeferredRatherThanFailed`, which
   returns true **only** for `CAMPAIGN_NOT_EXECUTABLE_STATE`; any other readiness failure
   marks the execution `FAILED`.
3. So the cause is **deterministic and derivable** from the live campaign status — a
   field the service already loads.

There was no persisted reason, no computed reason, and the only diagnostic was a
`log.info`. `CampaignExecutionResponse` had `failureReason` (set only on `FAILED`) and
nothing else. **Decision: derived, read-only. No migration.**

## 8. Pause/Resume Scenario Matrix

| # | Scenario | Observed behaviour (pre-VB-8H) | Post-VB-8H |
|---|---|---|---|
| A | SCHEDULED, no execution, operator pauses | campaign → PAUSED; nothing else | unchanged |
| B | execution REQUESTED, operator pauses | stays `REQUESTED`, `log.info` "deferred", retried each tick, **never failed** | unchanged + reason now visible (§F-8H-03) |
| C | execution RUNNING, operator pauses | **new dispatch stops**; attempts requeued `QUEUED` keeping attempt number; retries stop; active calls untouched; execution stays `RUNNING` | unchanged, and now every non-executable state is gated too |
| D | PAUSED, scheduler tick | `start-requested-executions` defers; `dial-due-attempts` requeues **before any budget**; no attempt created, no VB-6C hold, no VB-6D.3 consumption | unchanged |
| E | resume | `PAUSED → SCHEDULED`; the same execution continues; requeued attempts dispatch next tick; **no new execution needed** | unchanged |
| F | paused while calls connected | active calls **continue**; pause is checked only when dispatching a *new* attempt; nothing terminates a live call | unchanged |
| G | PAUSED indefinitely | execution stays `RUNNING` while attempts are `QUEUED` — legitimately unfinished, so no execution-level PAUSED state is needed | unchanged |
| H | all attempts finish while PAUSED | execution → `COMPLETED`/`FAILED`. `reconcileExecutionInternal` **never reads the campaign** | unchanged, now explicitly tested |

## 9. Active Call Behaviour

`OutboundDialService` checks the gate once, before dispatching an attempt. An attempt
already `IN_PROGRESS` returns earlier (line 206/248) and is never touched. No pause path
calls `mediaController`, hangs up a channel, or touches `CallSession`/`CallLeg`. **No
telephony behaviour changed in this phase**, and none was needed to.

The adopted invariant — *pause blocks new dispatch, never retroactively terminates an
established call* — was verified against the code before being adopted, not assumed.

## 10. Scheduler Behaviour

Eight steps, per-step failure isolation (VB-6E). Pause affects two:

- `start-requested-executions` → `CAMPAIGN_NOT_EXECUTABLE_STATE` → **defer**, stay
  `REQUESTED`. Only a non-deferable readiness failure marks `FAILED`.
- `dial-due-attempts` → gate → requeue, **before** any budget.

`reconcile-executions` is campaign-blind, so a paused campaign's finished execution still
settles. `reconcile-stale-calls` is campaign-blind, so VB-8E/8F/8G recovery is unaffected.

## 11. Snapshot Boundary

Live `Campaign` reads from execution/scheduler code, classified:

| Read | Site | Class |
|---|---|---|
| existence | `OutboundDialService` (missing → `CAMPAIGN_NOT_FOUND`) | existence check |
| **PAUSED (now: executable)** | `OutboundDialService` dispatch gate | **operational gate — approved** |
| `isExecutable` | `CampaignReadinessService` (pre-start gate) | operational gate — approved |
| snapshot config | `runtimeConfigResolver.resolve(execution)` everywhere else | snapshot (correct) |

**No unsafe mutable-configuration read exists in the execution path.** The invariant that
makes the two operational gates safe is
`CampaignLifecyclePolicy.editableAndExecutableAreDisjoint()` — configuration is mutable
only in `DRAFT`, which is never executable. Asserted again in this phase.

## 12. Multiple Execution Analysis

Allowed. Guarded only by `findByCampaignIdAndIdempotencyKeyAndDeletedAtIsNull`. There is
no "one active execution per campaign" constraint, and **none was added** — the brief
forbids adding uniqueness without an explicit product requirement. Consequence accepted:
campaign status cannot mirror any single execution, which is precisely why B9a must not
be given an engine producer.

### Two failed verification attempts, recorded rather than hidden

1. **Server restart mid-run.** The first full-suite run was killed with no `BUILD` line
   (~8k lines of partial output). Not a test result; the run was re-executed.
2. **Docker outage.** The second run reported 1815 / **119 errors**. Cause was
   `PSQLException: Connection to localhost:5432 refused` (×87) and
   `IllegalStateException: Previous attempts to find a Docker environment failed` — all
   nine user containers had gone down and restarted five minutes earlier. Re-running once
   Docker was healthy dropped errors to **0**, confirming the environment, not the code.

A third run then exposed **12 genuine failures in `OutboundDialServiceRoutingTest`** —
a real regression of mine, discussed below, and the reason this phase is honest about
its verification history.

### A real regression I introduced, and how it was fixed

Widening the dispatch gate from `== PAUSED` to `!isExecutable(...)` made the gate consult
the campaign lifecycle state where it previously did not. `OutboundDialServiceRoutingTest`
builds a `CampaignEntity` fixture with **no status at all**, so `isExecutable(null)` is
false, the attempt was requeued, and 12 cases expecting a dispatch outcome got `QUEUED`
instead.

**The production change is correct and was kept.** A `DRAFT` or `ARCHIVED` campaign must
not dispatch, and `EXECUTABLE_STATUSES` is the pre-existing authority for that. The
*fixture* was the unrealistic part: a real campaign always carries a status. That same
fixture had already been corrected once for the **execution** in VB-8D for the same class
of reason ("the fixture execution must be in a dispatchable state"), so the campaign side
was simply completing an existing correction. The fixture now sets
`CampaignStatus.SCHEDULED`, with a comment explaining why. **No assertion was weakened
and no test was disabled** — 12 previously-failing behaviours are green again.

## 21. Remaining Findings

- **F-8H-04 (MEDIUM, deferred) — `CampaignExecutionStatus.CANCELLED` has no producer.**
  No operator endpoint and no engine path. *Who* cancels and *when* is a product
  decision with no stated requirement. Inventing an endpoint would be the artificial
  state mutation this phase forbids. Recommended: a product decision first, then a phase.
- **F-8H-05 (INFO) — a paused execution with queued work stays `RUNNING` indefinitely.**
  Correct: the work is unfinished, so it must not be reported complete. If operations
  want a distinct "suspended" execution status, that is a new product concept, not a bug.
- **F-8H-02 (INFO, retained) — campaign `RUNNING` is an operator label, not a derived
  fact.** A campaign actively dispatching may read `SCHEDULED`. That is inherent to
  separating the two lifecycles; deriving it would reintroduce the ambiguity D10 rejects.
