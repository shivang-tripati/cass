# 02 — Call Flow

The central document for understanding how a call moves through this system.

**Status warning, please read first.** No call has been placed in this
environment yet. Phase B established the engine only. So this document
currently contains:

* **CONFIRMED** — component identities, identifiers, ports, and the exact
  command and event shapes the Java platform will use (read from the Java
  source and from FreeSWITCH source, and validated against a live FreeSWITCH
  for the *configuration* side).
* **NOT YET TESTED** — the end-to-end call sequences below. They are written
  from the Java contract plus FreeSWITCH's documented behaviour, and every one
  of them must be observed in a later phase before it may be relied upon.

Every diagram below is a *prediction to be verified*, not a report of
something observed. When a phase observes one, it converts the relevant labels
to CONFIRMED and adds the evidence.

## 1. The correlation chain

This is the most important thing in the whole system. If you understand one
thing, understand this.

```text
   Java                          FreeSWITCH                        Java
     │                              │                              │
     │  CallAttempt.id =            │                              │
     │  4f1c…  (a UUID)            │                              │
     │                              │                              │
     ├─ ESL: bgapi originate ──────►│                              │
     │   {origination_uuid=         │                              │
     │    4f1c…,                    │                              │
     │    origination_caller_id_    │                              │
     │    number=+15551234567}      │                              │
     │   sofia/gateway/fs-gateway/  │                              │
     │   15557654321                │                              │
     │                              │                              │
     │   reply: +OK Job-UUID: j7…    │  ← NOT a channel. Never      │
     │                              │    persisted as an identity  │
     │  (channel UUID is 4f1c…,     │                              │
     │   known BEFORE the call)     │                              │
     │                              │                              │
     │                              │──► SIP INVITE ──► provider  │
     │                              │◄── 100 Trying / 180 Ringing  │
     │                              │◄── 200 OK + SDP             │
     │◄── CHANNEL_ANSWER ───────────┤                              │
     │    Call-UUID: 4f1c…          │                              │
     │                              │                              │
     │  (Java matches Call-UUID     │                              │
     │   against call_attempts.     │                              │
     │   provider_call_id)           │                              │
     │                              │                              │
     │◄── PLAYBACK_START ───────────┤                              │
     │◄── PLAYBACK_STOP ────────────┤                              │
     │◄── CHANNEL_HANGUP ───────────┤                              │
     │    Call-UUID: 4f1c…          │                              │
     │    Hangup-Cause: NORMAL_     │                              │
     │      CLEARING                │                              │
     ▼                              ▼                              ▼
```

**Why the channel UUID is chosen rather than discovered.** `origination_uuid`
is a FreeSWITCH channel variable. By setting it, Java makes the channel's
identity deterministic *before* the call is placed. Without it, Java would have
to learn the channel UUID afterwards — by polling, or by waiting for a
`CHANNEL_CREATE` and guessing which background job it belonged to. Both are
racy. With it, every subsequent event correlates by exact equality.

**Where the SIP Call-ID is.** The SIP `Call-ID` is generated by whichever side
sends the INVITE — here, FreeSWITCH, so it is on the provider's side of the
dialog. It is visible to FreeSWITCH as the `sip_call_id` channel variable.
**NOT YET TESTED** in this environment. For a normal outbound campaign call
there is no SIP Call-ID on the Java side at all; Java only knows the channel
UUID. If you ever need to correlate with a carrier's records, the chain is
`channel UUID → sip_call_id → carrier CDR`, and it must be captured at call
time, because the channel is gone afterwards.

**CONFIRMED** (from the Java source, `EslClient.java`):

```java
String dialString = String.format("sofia/gateway/%s/%s", gateway, destinationNumber);
String originateCmd = String.format(
        "bgapi originate {origination_uuid=%s,origination_caller_id_number=%s}%s",
        channelUuid, callerId, dialString);
```

and the reply's `Job-UUID` is read only for logging.

## 2. Flow A — PLAYFILE (outbound voice campaign)

**NOT YET TESTED.** Predicted from the Java contract.

### 2.1 Sequence

```text
Java                FreeSWITCH                Gateway/Provider
 │                       │                            │
 │ 1 originate          │                            │
 │──────────────────────►│                            │
 │                       │ 2 build INVITE            │
 │                       │  {origination_uuid}        │
 │                       │───────────────────────────►│
 │                       │ 3 100 Trying               │
 │                       │◄───────────────────────────│
 │                       │ 4 180 Ringing             │
 │                       │◄───────────────────────────│
 │                       │ 5 200 OK + SDP            │
 │                       │◄───────────────────────────│
 │                       │ 6 ACK                     │
 │                       │───────────────────────────►│
 │ 7 CHANNEL_ANSWER      │                            │
 │◄──────────────────────┤                            │
 │ 8 uuid_broadcast      │                            │
 │    <uuid> <path> aleg │                            │
 │──────────────────────►│ 9 read file, encode, send │
 │                       │   RTP ────────────────────►│
 │ 10 PLAYBACK_START     │                            │
 │◄──────────────────────┤                            │
 │ 11 PLAYBACK_STOP      │                            │
 │◄──────────────────────┤                            │
 │ 12 uuid_kill NORMAL_  │                            │
 │    CLEARING           │                            │
 │──────────────────────►│ 13 BYE ──────────────────►│
 │ 14 CHANNEL_HANGUP     │                            │
 │◄──────────────────────┤                            │
 │    Hangup-Cause:      │                            │
 │    NORMAL_CLEARING    │                            │
 │                       │                            │
```

### 2.2 The eleven questions

**1. Who initiates?** Java, via ESL. It never speaks SIP.

**2. Which protocol?** ESL command to FreeSWITCH; FreeSWITCH then speaks SIP
and RTP to the far end.

**3. Which component receives it?** `mod_event_socket` receives the command;
`mod_sofia` builds and sends the SIP.

**4. Which UUID identifies the channel?** The `CallAttempt.id` that Java chose
via `origination_uuid`.

**5. Where is the SIP Call-ID?** FreeSWITCH-generated, on the outbound dialog;
visible only as the `sip_call_id` channel variable. Not present in Java.

**6. Where does RTP flow?** FreeSWITCH → provider, from a port in
30000-30099. In a later phase both sides are containers on `obd-telephony` and
this stays inside the Docker network.

**7. Which ESL events?** `CHANNEL_PROGRESS` (optional early media),
`CHANNEL_ANSWER`, `PLAYBACK_START`, `PLAYBACK_STOP` (or `PLAYBACK_ERROR`),
`CHANNEL_HANGUP`.

**8. Which Java service consumes them?** `EslEventService` routes every event.
`CHANNEL_ANSWER` fires the playback trigger; `PLAYBACK_STOP` triggers teardown;
`CHANNEL_HANGUP` is the authoritative finalisation and the only place the
capacity reservation is released.

**9. What indicates success?** `PLAYBACK_STOP` followed by `CHANNEL_HANGUP`
with `Hangup-Cause: NORMAL_CLEARING`. A hangup *during* playback with a normal
cause is treated by the platform as a **delivered** call — a deliberate product
decision, not an accident.

**10. What indicates failure?** `PLAYBACK_ERROR` (media could not be played —
mapped to a temporary failure so the platform may retry), or a `CHANNEL_HANGUP`
carrying a cause other than normal clearing (mapped through
`HangupCauseMapper`).

**11. Where should an engineer look if it fails?**

```text
No CHANNEL_ANSWER at all   -> originate rejected / gateway / SIP signalling
   sofia status gateway ; FreeSWITCH console log
CHANNEL_ANSWER but no      -> the media path
PLAYBACK_START               is /media/obd present and is the file readable
PLAYBACK_START then        -> playback aborted; check the Playback-Error
PLAYBACK_ERROR                header on the event
No CHANNEL_HANGUP at all   -> ESL subscription, or Java crashed mid-call
```

## 3. Flow B — DTMF / IVR

**NOT YET TESTED.** Predicted from the Java contract.

### 3.1 Sequence (the first digit)

```text
Java                FreeSWITCH                Endpoint (callee)
 │                       │                            │
 │ 1 originate          │                            │
 │──────────────────────►│ 2 INVITE ────────────────►│
 │                       │◄── 200 OK ────────────────│
 │ 3 CHANNEL_ANSWER      │                            │
 │◄──────────────────────┤                            │
 │ 4 uuid_broadcast      │                            │
 │    <uuid> <prompt>    │                            │
 │──────────────────────►│ 5 prompt audio RTP ──────►│
 │ 6 PLAYBACK_START      │                            │
 │◄──────────────────────┤                            │
 │ 7 PLAYBACK_STOP       │                            │
 │◄──────────────────────┤                            │
 │ 8 **Java now arms     │                            │
 │    collection in the  │                            │
 │    database only.**   │                            │
 │    Nothing is sent    │                            │
 │    to FreeSWITCH.     │                            │
 │                       │                            │
 │                       │◄── 9 DTMF "1" (RTP       │
 │                       │    telephone-event, or SIP │
 │                       │    INFO)                  │
 │ 10 CHANNEL_DTMF       │                            │
 │◄──────────────────────┤                            │
 │    DTMF-Digit: 1      │                            │
 │                       │                            │
 │ 11 digit + config     │                            │
 │    classify -> store  │                            │
```

### 3.2 The critical, counter-intuitive fact

**Java never asks FreeSWITCH to collect DTMF.** There is no `uuid_dtmf`, no
`read`, no `play_and_collect_digits`, no `CHANNEL_EXECUTE` anywhere in the Java
platform. The `VoiceMediaController.collectDtmf(...)` method exists in the
interface but throws `UnsupportedOperationException` and is never called from
production code.

Collection is armed **in the database** and is driven purely by incoming
`CHANNEL_DTMF` events plus a Java-side timeout.

**Therefore FreeSWITCH must be configured to *emit* the event and must NOT be
configured to run a digit-collection application.** A dialplan that captures
digits itself would consume them and Java would never see them — and it would
also change the A-leg media model that `aleg` playback depends on.

### 3.3 The eleven questions

**1. Who initiates?** The endpoint presses a key. Java only listens.

**2. Protocol?** RFC 2833/4733 inside RTP, or SIP INFO over the SIP dialog.
Both must work, which is why `liberal-dtmf=true` is set — the stock default
`false` accepts only the profile's preferred method and **silently drops** the
other.

**3. Who receives it?** `mod_sofia`, on the campaign channel. It emits
`CHANNEL_DTMF` with header `DTMF-Digit`.

**4. Which UUID?** The same pinned channel UUID as the whole call.

**5. SIP Call-ID?** As Flow A.

**6. RTP?** Carries RFC 2833 telephone-event packets. SIP INFO does not use RTP
at all — which makes INFO the more robust path when media is broken.

**7. Events?** `CHANNEL_DTMF`, one per digit.

**8. Java consumer?** `EslEventService.handleChannelDtmf` → the DTMF collector
trigger → digit classification (`COLLECTING` / `VALID` / `INVALID` / `TIMEOUT`).

**9. Success?** The expected digit sequence arrives and is classified `VALID`.

**10. Failure?** Nothing arrives at all (transport), or digits arrive that do
not match the expected prefix (classification → `INVALID`).

**11. Where to look if digits are missing?**

```text
Confirm the endpoint registered and the call is bridged
   sofia status profile internal  -> REGISTRATIONS
Confirm the profile's DTMF policy
   grep liberal-dtmf / proxy-info in the profile XML
Confirm RTP is actually flowing (RFC 2833 needs media)
   see 07-RTP-AND-MEDIA.md
Try SIP INFO instead (avoids the media dependency)
Confirm Java is subscribed and is reading DTMF-Digit
   DTMF-Digit must be a SINGLE character; an encoding like "10" for "*"
   would be rejected by the platform
```

## 4. Flow C — CONNECT_BY_AGENT (two legs and a bridge)

**NOT YET TESTED.** Predicted from the Java contract.

### 4.1 Sequence

```text
Java            FreeSWITCH         Customer leg       Agent leg
 │                   │                    │                 │
 │ 1 originate       │                    │                 │
 │   (customer)      │                    │                 │
 │──────────────────►│ 2 INVITE ───────────────────────────► │
 │                   │◄── 200 OK ────────────────────────── │
 │ 3 CHANNEL_ANSWER  │                    │                 │
 │◄──────────────────┤                    │                 │
 │                   │                    │                 │
 │ 4 originate       │                    │                 │
 │   (agent leg,     │                    │                 │
 │    fresh UUID)    │                    │                 │
 │──────────────────►│ 5 INVITE ───────────────────────────► │
 │                   │◄── 100 Trying / 180 Ringing ───────── │
 │ 6 CHANNEL_PROGRESS│ (agent leg)       │                 │
 │◄──────────────────┤                    │                 │
 │                   │◄── 200 OK (agent answers) ─────────── │
 │ 7 CHANNEL_ANSWER  │                    │                 │
 │◄──────────────────┤  (agent leg)      │                 │
 │                   │                    │                 │
 │ 8 uuid_bridge     │                    │                 │
 │   <caller>        │                    │                 │
 │   <agent>         │                    │                 │
 │──────────────────►│ 9 media now flows between the legs    │
 │                   │                    │                 │
 │ 10 CHANNEL_BRIDGE │                    │                 │
 │◄──────────────────┤  Call-UUID      = caller channel      │
 │    Bridge-B-      │  Bridge-B-Unique = AGENT channel       │
 │    Unique-ID:     │                    │                 │
 │    <agent uuid>   │                    │                 │
 │                   │                    │                 │
 │ 11 (conversation) │◄════════ RTP both ways ══════════════►│
 │                   │                    │                 │
 │ 12 CHANNEL_HANGUP │                    │                 │
 │◄──────────────────┤  (either leg)    │                 │
```

### 4.2 The eleven questions

**1. Who initiates?** Java, twice — once for the customer leg, once for the
agent leg.

**2. Protocol?** Identical to Flow A for both. Same gateway mechanism.

**3. Who receives?** `mod_sofia`, on two separate channels.

**4. Which UUIDs?** Two distinct ones. The customer leg uses the pinned
`CallAttempt.id`. The **agent leg uses a fresh random UUID generated inside
`EslClient`**, because an agent leg is not attached to a `CallAttempt`. Each is
persisted as the `provider_call_id` of its own `CallLeg`.

**5. SIP Call-ID?** One per leg; they are separate dialogs.

**6. RTP?** Customer leg and agent leg each have their own RTP session with the
far end. The bridge relays between them — the audio is not end-to-end.

**7. Events?** `CHANNEL_PROGRESS`, `CHANNEL_ANSWER` (agent leg),
`CHANNEL_BRIDGE`, then `CHANNEL_HANGUP` on either leg.

**8. Java consumer?** `EslEventService` routes agent-leg events (matched by
the leg's own `provider_call_id`) to the agent connect boundary. The bridge
event is matched by **`Bridge-B-Unique-ID`**, not by the event's own `Call-UUID`.

**9. Success?** A `CHANNEL_BRIDGE` event whose `Bridge-B-Unique-ID` equals the
agent channel's UUID. The `uuid_bridge` command returning `+OK` is **not**
sufficient.

**10. Failure?** The agent leg hangs up before the bridge (classified
`AGENT_NO_ANSWER`), or the bridge command is rejected, or a `CHANNEL_HANGUP`
arrives on the agent leg that never reached `BRIDGED`.

**11. Where to look if it fails?**

```text
Agent leg never rings      -> the agent endpoint's dial_target, and the fact
                              that it must be reachable THROUGH the gateway
                              (see below)
Bridge never confirmed     -> the two UUIDs; is the anchor really the caller
                              leg?  sofia status / show bridges
Bridge confirmed but no    -> media path, or proxy-info for SIP INFO relay
audio                         between bridged legs
```

### 4.3 Two traps specific to this flow

**Trap 1 — the anchor leg.** `uuid_bridge` takes two channel UUIDs and the
first is the anchor. The platform always passes the **caller** leg first. If
you ever run this by hand, swapping the arguments changes which side is treated
as the A-leg, which changes `aleg` playback behaviour.

**Trap 2 — the agent endpoint must be reachable through a gateway.** Java
builds the agent leg with the *same* `sofia/gateway/<gw>/<dest>` form as the
customer leg, and the agent leg is originated with a **null** gateway name,
which falls back to `telephony.freeswitch.gateway`. A softphone registered on
the `internal` profile of the *same* FreeSWITCH is therefore **not** reachable
that way. This is why the agent will be expected to sit on the far side of the
gateway — a constraint imposed by the existing Java dial-string contract, not a
preference. Recorded in the Phase C plan.

## 5. Flow D — inbound (informational, not implemented here)

**NOT YET TESTED.** The Java platform has an inbound path that watches for
`CHANNEL_CREATE` with `Call-Direction: inbound`, but no inbound call can occur
in Phase B because nothing registers and no dialplan routes a DID.

The two requirements that will apply when it is tested:

1. The dialplan must route the dialled DID into the platform's own context and
   **must not** hand the channel to an application such as `voicemail` or
   `voiceportal`. If it does, the channel is consumed before Java sees the
   answer event and the session stalls.
2. Java does not answer the call. It creates a session in its initial state and
   waits for `CHANNEL_ANSWER` / `CHANNEL_HANGUP` on the same channel UUID.

## 8. PHASE C: what was actually observed, against the predictions above

Sections 2 to 4 are **predictions from the Java contract**, written before any
call was placed. Phase C placed real calls and observed the FreeSWITCH side. This
section records the deltas.

**Nothing above has been deleted or edited to look correct.** Where an observation
contradicts a prediction, both are kept and the difference is explained, because
the delta is the useful part.

### 8.1 Summary of the deltas

| # | Predicted (Phase B) | Observed (Phase C) | Severity |
|---|---|---|---|
| D1 | channel UUID is reported as `Call-UUID` | **no such header**; it is `Channel-Call-UUID` / `Unique-ID` | **breaks correlation** |
| D2 | a bad media path produces `PLAYBACK_ERROR` / `Playback-Error` | **no event at all**; log-only | undetectable as designed |
| D3 | `origination_uuid` identifies the channel for the call's lifetime | **does not survive a dialplan transfer**; a new UUID is minted | later commands hit a dead channel |
| D4 | `user/<ext>` is a usable dial string | `CHAN_NOT_IMPLEMENTED`; `{$dialed_domain}` is unexpanded | local test form only |
| D5 | `+OK` on a command means it worked | `+OK Job-UUID` means the task was **queued** | false PASS risk |
| D6 | RTP range unverifiable without a call | ports readable on live channels: 30022-30082 | question closed |
| D7 | a host softphone could participate in media | the host has **no route** to the bridge network | topology change |

### 8.2 D1 - the correlation header does not exist

**Predicted** (section 1 of this file, and Phase B): every `CHANNEL_*` event
carries `Call-UUID`, and that is what correlates an event to a `CallAttempt`.

**Observed**, on all five event types captured with unfiltered header dumps:

```text
Unique-ID          = 348eecfb-7d68-48f8-a566-3cac24e4a8cc
Channel-Call-UUID  = 348eecfb-7d68-48f8-a566-3cac24e4a8cc
Caller-Unique-ID   = 348eecfb-7d68-48f8-a566-3cac24e4a8cc
variable_call_uuid = 348eecfb-7d68-48f8-a566-3cac24e4a8cc
Call-UUID          = ABSENT
```

**Deviation.** `EslEvent.getCallUuid()` reads `Call-UUID` and therefore returns
`null` for every event.

**Impact.** No event correlates to a `CallAttempt`. `EslEventService`'s
`log.warn("Received ESL event without Call-UUID: ...")` fires on every event. The
practical effect is that calls never complete from the platform's point of view,
because the hangup is correlated by UUID.

**Root cause.** A documented-but-unverified assumption. FreeSWITCH emits the
channel UUID under several names; `Call-UUID` is not among them on this build.

**Resolution.** Not fixed in Phase C - the Java application is a separate
workstream. Identified fix: read `Channel-Call-UUID`, falling back to
`Unique-ID`. Recorded as defect **J1**.

**Additional observed detail:** header **values are URL-encoded**. `+` appears as
`%2B` and `@` as `%40`, so `Caller-Caller-ID-Number` arrives as
`%2B15551230000`. A literal comparison against `+15551230000` will not match.

### 8.3 D2 - a failed playback produces no event

**Predicted:** `uuid_broadcast` with a bad path yields `PLAYBACK_ERROR` carrying a
`Playback-Error` header. The project's own tests assumed values such as
`FILE_NOT_FOUND` and `RESOURCE_ERROR`.

**Observed:**

```text
uuid_broadcast <uuid> /media/obd/phase-c-deliberately-absent.wav aleg
  reply          -> +OK Message sent
  PLAYBACK_ERROR -> not emitted
  PLAYBACK_START -> not emitted
log -> [WARNING] mod_sndfile.c:281 Error Opening File
       [/media/obd/phase-c-deliberately-absent.wav]
       [System error : No such file or directory.]
```

**Deviation.** There is no error event. The command reports success.

**Impact.** A call whose audio is missing is indistinguishable from a call playing
nothing, indefinitely.

**Root cause.** Playback never begins, so no playback events are generated at all.
The failure is reported only by the file layer.

**Resolution.** Detecting this requires treating the **absence** of
`PLAYBACK_START`/`PLAYBACK_STOP` within a window as the failure signal. Recorded
as defect **J2**.

### 8.4 D3 - the pinned UUID does not survive a transfer

**Predicted:** pinning `origination_uuid` makes channel identity deterministic, so
later `uuid_broadcast` / `uuid_kill` address the same channel.

**Observed.** The pin works at originate time - `CHANNEL_CREATE` carries
`variable_origination_uuid` equal to the supplied value. But the stock dialplan
then transfers the channel:

```text
EXECUTE [depth=0] ... transfer(1002 XML default)
[NOTICE] switch_ivr.c:2303 Transfer sofia/internal/+15551230000@172.25.0.2 to XML[1002@default]
```

and a **new channel with a new UUID** is created. The original is gone.

**Impact.** `uuid_broadcast` and `uuid_kill` addressed to the pinned UUID target a
channel that no longer exists - the agent leg of a CONNECT_BY_AGENT call, and the
PLAYFILE target, would silently do nothing.

**Root cause.** Relying on the stock dialplan, whose transfer semantics are
incompatible with the platform's UUID-pinning contract.

**Resolution.** Replace the stock dialplan with an explicit one that bridges
without transferring away from the pinned channel. This is the first item of the
next phase. Recorded as defect **J3**.

### 8.5 D4 - `user/...` is not a valid originate URL

```text
Cannot create outgoing channel of type [1002@{$dialed_domain}]
  cause: [CHAN_NOT_IMPLEMENTED]
```

`{$dialed_domain}` is a **dialplan** variable and is unexpanded at originate time.
`user/<ext>` is a dialplan target resolved through the directory's `dial-string`,
not an originate URL.

Measured matrix:

| Dial string | Channel | Answered | Bridged |
|---|---|---|---|
| `user/1002` | no | - | - |
| `user/1002 &park()` | no | - | - |
| `user/1002 1002` | no | - | - |
| `user/1002 &park() 1002` | no | - | - |
| `sofia/internal/1002@172.25.0.2 &park()` | **yes** | **yes** | **yes** |
| `loopback/dial/user/1002` | yes | no | no |

`sofia/internal/...` is the working local form, and is the closest analogue of
the production `sofia/gateway/<gw>/<dest>`.

### 8.6 D5 - `+OK` is not success

```text
bgapi originate {origination_uuid=<uuid>}user/1002
  reply    -> +OK Job-UUID: f1d32e2f-...
  channels -> 0 total
log -> [WARNING] switch_ivr_originate.c:2324 No origination URL specified!
```

The command was accepted; the task then failed with no feedback. **The only
trustworthy success signals are `CHANNEL_CREATE` with the pinned `Unique-ID`, and
then `CHANNEL_ANSWER`.**

A related harness lesson: do **not** issue a synchronous command on a connection
that is also receiving subscribed events. It can read the next *event* instead of
the reply, leaving the real reply queued and every later read off by one frame.
The symptom is a command that times out against a perfectly healthy switch. Use a
second connection for commands.

### 8.7 D6 - RTP allocation is now observable

Phase B could not read the effective range at rest. On a live call:

```text
uuid_getvar <leg> local_media_port   -> 30022, 30028, 30036, 30070, 30082
```

all inside `30000-30099`, and also visible in `CHANNEL_CREATE` as
`variable_local_media_port` before the call is answered. **The question Phase B
left open is closed.** See [07](07-RTP-AND-MEDIA.md) 11.1.

Note what this does **not** prove: a port was allocated. It does not prove audio
arrived. See 8.8.

### 8.8 The three claims, kept separate

This is the discipline Phase C most needs to impose, because conflating them
produced a false PASS in Phase B and nearly did again in Phase C.

| Claim | Status | Evidence |
|---|---|---|
| SIP signalling works (INVITE, 200 OK, BYE) | **CONFIRMED - LOCAL** | observed on a real call |
| RTP is allocated in the configured range | **CONFIRMED - LOCAL** | ports 30022-30082 |
| audio crosses the network both ways | **NOT YET TESTED** | the observed bridge was between two platform-side legs |

The bridge observed during Phase C had both legs reporting
`remote_media_ip = 172.25.0.2`. The endpoint's leg was not proven to be part of
it. Closing this requires the dialplan replacement in D3, then reading the
**endpoint's** counters - this build has no RTP counter channel variable, and
`uuid_debug_media` is a toggle, not a statistics command
([13](13-TROUBLESHOOTING.md) entry 17).

### 8.9 D7 - a host softphone cannot carry media

Measured, not assumed: the Windows host has no route to `172.25.0.0/16`. A host
endpoint can register and can originate, and can do nothing else. See
[ADR-004](decisions/ADR-004-local-endpoints-in-docker-network.md).

## 9. PHASE D: what changed after Phase C raised these

Section 8 recorded the Phase C deltas as open. Phase D acted on three of them
and proved a fourth assumption wrong. Nothing above has been edited: the
predictions stay visible, and this section records what happened.

| Delta | Phase C finding | Phase D outcome |
|---|---|---|
| **D1** | no `Call-UUID` header; identity is `Channel-Call-UUID` / `Unique-ID` | **FIXED** — correlation now resolves in header order, live-verified |
| **D2** | no `PLAYBACK_ERROR` for a missing file | **FIXED** — failure is detected from the real lifecycle, live-verified |
| **D3** | a transfer mints a new channel UUID | **NO CODE CHANGE** — the pinned identity was measured to stay addressable |
| **D4** | *(new in Phase D)* channel commands need an `api` prefix | **FIXED** — they were being rejected outright |

### 9.1 D1 — the correlation chain now works

The chain in section 1 of this file predicted `Call-UUID` at each step. It is now:

```text
CHANNEL_* event
    │  Channel-Call-UUID  (fallback: Unique-ID, then Call-UUID for compat)
    ▼
EslEvent.getCallUuid()
    ▼
CallSession.providerCallId  /  CallAttempt.providerCallId   (the pinned UUID)
```

Live-verified: a real `CHANNEL_CREATE` carries **no** `Call-UUID`, and the
pinned UUID resolves from the headers that are actually present.

### 9.2 D2 — playback outcomes are now distinguishable

The prediction was that a bad path yields `PLAYBACK_ERROR` with a
`Playback-Error` header. It does not. The real discriminator, measured:

| Case | Command reply | Events |
|---|---|---|
| valid | `+OK Message sent` | `PLAYBACK_START`, `PLAYBACK_STOP` |
| missing | `+OK Message sent` | *(neither)*, then `CHANNEL_EXECUTE_COMPLETE` |

So the rule the platform now applies is: **`CHANNEL_EXECUTE_COMPLETE` closes the
request; if no `PLAYBACK_START` arrived, the accepted command produced no
audio.** A missing asset is classified as a media failure rather than sitting in
`ANSWERED` until the maximum-duration sweeper mislabels it.

### 9.3 D3 — the pinned identity is addressable, so no new model is needed

D8.4 recorded that a dialplan transfer mints a new UUID. That is true of the
**bridge participants**, and the pinned leg is not one of them:

```text
pinned 34b5c6c8  CHANNEL_CREATE, CHANNEL_ANSWER, CHANNEL_EXECUTE
3aa6cc08         ... CHANNEL_BRIDGE          <- bridge anchor, not the pinned leg
```

What Phase D then measured is the part that matters for the application: while
the call was bridged, the pinned UUID still worked for both media and hangup.

```text
api uuid_broadcast <pinned> <file> aleg -> PLAYBACK_START/STOP on <pinned>
api uuid_kill <pinned> NORMAL_CLEARING  -> CHANNEL_HANGUP on <pinned>
```

**Conclusion.** The existing model — supply the UUID, store it as
`providerCallId`, address that leg with it — is correct. A "current channel"
abstraction was considered and **rejected on the evidence**, because the observed
behaviour does not require it.

**What the documentation must no longer imply:** that the pinned UUID is the
only channel in play. It is the *addressable identity of the leg the application
originated*. Other channels exist on the far side of the bridge, and no header
links them to the pinned one.

### 9.4 D4 — the media and hangup commands were never being accepted

Found by running the real client against the real switch, after every test had
passed:

```text
uuid_kill <uuid> NORMAL_CLEARING   -> -ERR command not found
api uuid_kill <uuid> NORMAL_CLEARING -> accepted
```

See `05-ESL.md` 12.1. This is the defect with the widest blast radius in the
whole engagement: every playback, hangup and bridge would have been refused, so
no call could ever have completed. It is also the clearest argument for the rule
this file has been building towards — a test double that answers success to
everything it does not recognise is worse than no double at all.

## 10. PHASE E: the flow, end to end, with the peer as witness

Section 9 recorded the Java/ESL contract as hardened. Phase E made one shape of
this flow actually reach an endpoint. The sequence below is the measured one,
from `sofia/gateway/local-endpoint-1002/1002` to hangup.

```text
Java dial string      sofia/gateway/local-endpoint-1002/1002
       │             (no domain - the gateway supplies it; see ADR-007)
       ▼
gateway               Profile internal, Realm <switch domain>,
                      Proxy sip:endpoint-b:5060, register=false
       ▼
route                 the endpoint's REGISTRATION contact, in sofia_reg_internal.
                      mod_sofia routes by domain and will not use the endpoint's
                      address directly - every direct form is NO_ROUTE_DESTINATION
       ▼
SIP INVITE            endpoint logs: receiving invite from <switch>:5060
       ▼
answer                endpoint CHANNEL_ANSWER (peer-witnessed, not the local event)
       ▼
media                 local_media  172.25.0.3:30078
                      remote_media 172.25.0.4:31378
                      PCMU both ways
       ▼
peer media            endpoint plays its tone; platform receives +64 UDP datagrams
       ▼
hangup                DESTINATION_OUT_OF_ORDER
```

**THE ORDER OF PROOF MATTERS MORE THAN THE SEQUENCE.** The platform reported
`CHANNEL_ANSWER` for a version of this flow that never left the machine, because
the stock dialplan answered the dialstring with `voicemail`. Every signal
available on the local switch said success. Only the peer's own state - a channel
of its own, an SDP exchanged, counters that moved - distinguished the real call
from the fake one.

So the correlation chain is now two-sided:

```text
CallAttempt  <-providerCallId->  channel UUID  (local, from events)
                                      │
                                      └── SIP Call-ID  -> peer's own channel
```

The second half is what makes the first half trustworthy. See `06-SIP.md` 12.4
and troubleshooting entry 24.

**Still open:** the platform-to-endpoint media leg is not proven, so
**TWO-WAY AUDIO REMAINS NOT PROVEN**; and PLAYFILE's `uuid_broadcast` returns
`-ERR invalid uuid` against a live answered channel while `uuid_dump` on the
same UUID succeeds. Both are recorded in
[`LIVE-FREESWITCH-PHASE-E.md`](../LIVE-FREESWITCH-PHASE-E.md) §8 and §9.
